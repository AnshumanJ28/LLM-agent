# From-Scratch Autonomous Agent — Full Project Spec

## What this is
A tool-using ReAct agent built entirely from scratch (no LangChain/LangGraph/CrewAI).
Every piece — the reasoning loop, tool schemas, memory, evaluation harness, tracing, and
sandboxed code execution — is hand-rolled to demonstrate a real understanding of how
agent systems work under the hood.

**LLM provider:** Groq API (`llama-3.3-70b-versatile`), via the `groq` Python SDK.
**API keys needed:** `GROQ_API_KEY` (required), `TAVILY_API_KEY` (for real web search;
optional — can be mocked).

## 1. Agent Loop (`src/agent/loop.py`)

### Pattern: ReAct (Reason + Act)
Model output must follow this exact structured format so it can be parsed reliably:

```
Thought: <reasoning about what to do next>
Action: <tool_name>
Action Input: <JSON object matching the tool's input schema>
```
or, when done:
```
Thought: <final reasoning>
Final Answer: <answer to the user>
```

### System prompt must include
1. The exact format above, stated explicitly with a worked example.
2. Tool list: name, description, JSON input schema (generated by `registry.py`, not
   hand-typed per tool).
3. Instruction: emit exactly one Thought/Action/Action Input block per turn, then stop.
4. A dynamic step-budget reminder injected as remaining steps shrink.

### Core function signature
```python
def run_agent(
    task: str,
    tools: dict[str, Callable],
    max_steps: int = 8,
    trace_logger: TraceLogger | None = None,
) -> AgentResult:
    ...
```

### Step logic
1. Build system prompt from the tool registry.
2. `transcript = [{"role": "system", ...}, {"role": "user", "content": task}]`.
3. Loop up to `max_steps` times:
   - Call Groq chat completion with the current transcript.
   - Parse for `Final Answer:` (return + stop) or `Action:` + `Action Input:` (dispatch).
   - **Parsing must be defensive** — regex-based, never crashes on malformed output.
     On a parse failure, append a corrective system message and retry (cap retries per
     step, e.g. 2).
   - Unknown tool name → feed back an error Observation, don't crash.
   - `Action Input` JSON parse failure → feed back a JSON-format error Observation.
   - Dispatch to the tool inside try/except; tool exceptions become
     `Observation: Error: <message>`.
   - Append assistant turn + Observation to transcript.
   - Log the full step (thought, action, input, observation, latency, token usage) via
     `trace_logger`.
4. If `max_steps` reached with no Final Answer, return `incomplete: True` with the
   transcript — never silently claim success.

### Return type
```python
@dataclass
class AgentResult:
    final_answer: str | None
    transcript: list[dict]
    steps_taken: int
    incomplete: bool
    total_tokens: int
```

### Error philosophy
Nothing in the loop should let a malformed response, unknown tool, or tool exception
crash the process. Every failure becomes an Observation the model can recover from, or —
past retry limits — a clean `incomplete` result. This robustness is the main engineering
signal of the whole project.

## 2. Tool Registry (`src/tools/registry.py`)

- Each tool is a plain Python function with a docstring describing its purpose and a
  type-hinted signature.
- `registry.py` introspects each function (via `inspect.signature` + docstring parsing)
  to auto-generate the JSON schema fed into the system prompt — don't hand-write schemas
  per tool; generate them so adding a tool is just writing the function.
- `register(fn)` decorator or explicit `TOOLS = {"web_search": web_search, ...}` dict —
  keep dispatch a simple lookup, no magic.

### `web_search.py`
- Calls Tavily API (`tavily-python` SDK) if `TAVILY_API_KEY` is set; otherwise returns a
  clearly labeled mock response so the rest of the system still runs offline.

### `code_exec.py`
- Does **not** run code in-process or via bare subprocess.
- Uses the `docker` Python SDK to spin up a sibling container from the `sandbox_exec`
  image per call: `network_disabled=True`, `mem_limit="128m"`, `nano_cpus` capped,
  `read_only=True`, `remove=True`.
- Enforce a wall-clock timeout in Python (kill/remove the container if it overruns).
- Capture stdout/stderr, log container ID + exit code + duration to the trace.

### `vector_lookup.py`
- Reuses the FAISS index approach from your `rag-document-qa` project — load a
  pre-built index, embed the query, return top-k chunks with scores.

### `calculator.py`
- Safe expression evaluation only (e.g. `asteval` or a restricted AST-walking evaluator)
  — never a bare `eval()`.

## 3. Memory (`src/agent/memory.py`)

- **Short-term:** the running transcript itself; once it exceeds a token budget you
  compute (via `tiktoken` or Groq's reported usage), summarize the oldest turns into a
  condensed note rather than truncating blindly.
- **Long-term:** a simple key-value or embedding-based store the agent can explicitly
  write to (`remember(key, value)`) and query (`recall(query)`) as its own tool — this
  ties directly into the vector-DB concepts you're currently studying.

---

## 4. Evaluation Harness (`src/eval/`)

This is what makes the project read as engineering, not a demo reel.

- `golden_set.json`: 20-30 hand-written tasks, each with an expected tool-call sequence
  and/or expected final-answer content.
- `judge.py`: a second Groq call scoring groundedness/correctness against the golden
  answer, plus rule-based checks (right tool called? stayed under step budget?).
- `run_eval.py`: runs the full suite, outputs a scorecard — pass rate, avg steps, avg
  latency, avg token cost. Track this over commits the way you tracked RMSE/MAE with
  MLflow in the forecasting project.

---

## 5. Tracing (`src/trace/logger.py`)

- Every step (thought, action, input, observation, latency, tokens) logged as one JSON
  line per step to `traces/<run_id>.jsonl`.
- `viewer/app.py` (Streamlit) reads a trace file and replays it step-by-step — this is
  your demo surface for recruiters/interviewers.

---

## 6. Guardrails (`src/guardrails/limits.py`)

- Step-count and cost ceilings enforced in code (checked before each model call), not
  just prompted for.
- Input sanitization before dispatch, especially into `code_exec`.
- Output schema validation before accepting a Final Answer, if the task expects
  structured output.

## 7. Docker Setup

### `Dockerfile.sandbox` (the important one)
```dockerfile
FROM python:3.11-slim
RUN useradd -m sandboxuser
USER sandboxuser
WORKDIR /tmp/exec
ENTRYPOINT ["python", "-c"]
```
No network, non-root, ephemeral, `read_only` filesystem at run time.

### `docker-compose.yml` shape
```yaml
services:
  app:
    build:
      context: .
      dockerfile: docker/Dockerfile.app
    ports:
      - "8000:8000"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock   # lets code_exec spawn sandbox containers
    environment:
      - GROQ_API_KEY=${GROQ_API_KEY}
      - TAVILY_API_KEY=${TAVILY_API_KEY}
    depends_on:
      - viewer

  viewer:
    build:
      context: .
      dockerfile: docker/Dockerfile.viewer
    ports:
      - "8501:8501"
    volumes:
      - ./traces:/app/traces
```

Sandboxing approach: **sibling container per execution** (Docker-out-of-Docker via the
mounted host socket), not true Docker-in-Docker — simpler, avoids privileged-mode and
storage-driver complexity, and still demonstrates real isolation.

## 8. API layer (`api/main.py`)

- FastAPI wrapping `run_agent`: `POST /run` accepts `{"task": "..."}`, returns
  `AgentResult` as JSON.
- Writes the trace file for each run so the viewer can pick it up immediately.

## 9. CI (`.github/workflows/ci.yml`)

- Runs `pytest` (unit tests for loop parsing, tool dispatch, guardrails) and
  `run_eval.py` (the golden-set scorecard) on every push.
- Fail the build if pass rate on the golden set drops below a threshold — this is your
  regression gate, same idea as the drift-monitoring gate in your MLOps project.

## Build order (suggested)
1. `agent/loop.py` + one trivial tool (`calculator.py`) — get the ReAct loop working
   end-to-end with the simplest possible tool.
2. `tools/registry.py` — generalize schema generation so adding tools is easy.
3. `web_search.py`, `vector_lookup.py` — real tools.
4. `trace/logger.py` + `viewer/app.py` — get visibility into what the agent is doing.
5. `guardrails/limits.py` — lock down step/cost budgets.
6. `code_exec.py` + both Dockerfiles + `docker-compose.yml` — sandboxed execution.
7. `eval/` — golden set, judge, scorecard.
8. `api/main.py` + CI wiring last, once the core loop is stable.
